# Inventory & Order Management API


A REST API for managing products, stock levels, and customer orders. Order placement is fully transactional: stock is locked, checked, and deducted atomically, and the whole operation rolls back on failure, so inventory never goes out of sync and items are never oversold, even under concurrent requests.

## How Order Placement Works

`POST /orders` runs inside a single database transaction (`app/services/order_service.py`):

1. Validate the payload with Pydantic and merge duplicate lines for the same product.
2. Lock the affected product rows with `SELECT ... FOR UPDATE`, **in ascending id order**.
3. Verify every line has enough stock (`404` if a product doesn't exist, `409` if stock is short).
4. Deduct stock and create the order and its items, snapshotting each unit price.
5. Commit. If anything fails at any step, the transaction is rolled back and nothing changes.

Why this is safe:

- **No overselling**: competing orders for the same product queue on the row lock; the second one sees the updated stock and fails with `409`.
- **No deadlocks**: because locks are always taken in id order, an order for `[A, B]` and another for `[B, A]` can't wait on each other.
- **All or nothing**: one short line item cancels the entire order, leaving every product untouched.
- **Last line of defence**: a database `CHECK (stock_quantity >= 0)` constraint backs up the application logic.

## SQL Reports

The report queries live in [`sql/`](sql/) as plain SQL and are executed by `app/services/report_service.py` with bound parameters:

- **`low_stock.sql`**: products whose `stock_quantity` is at or below a threshold. By default each product's own `low_stock_threshold` is used; pass `?threshold=` to override it for all products. Sorted lowest stock first.
- **`sales_report.sql`**: joins `order_items`, `orders`, and `products` to aggregate units sold and revenue per product for confirmed orders in a date range (UTC days, both ends inclusive), sorted by revenue.

What's covered:

- **Products & stock**: CRUD, pagination, validation, duplicate SKUs, stock never negative, deleting products that have orders.
- **Orders**: totals and stock deduction, merged duplicate lines, price snapshots, `404`/`409`/`422` paths, and **rollback** when one line is short or when a failure is injected mid-transaction.
- **Concurrency**: 20 simultaneous single-unit orders on 5 units of stock yield exactly 5 successes and 15 `409`s with final stock `0`; multi-unit contention never exceeds stock; opposite-order multi-product orders complete without deadlocks.
- **Reports**: threshold logic, overrides, per-product aggregation, empty ranges, date validation.

## Design Notes

- **Pessimistic locking** (`SELECT ... FOR UPDATE`) was chosen over optimistic retries: stock contention is exactly where pessimistic locking is simplest and most predictable.
- **Money** is stored as `NUMERIC` and handled as `Decimal`, never floats.
- **Stock changes only through `/stock` and orders**, so `PUT /products/{id}` deliberately ignores `stock_quantity`.
- **Schema changes** go through Alembic migrations (`alembic revision --autogenerate -m "..."`), never `create_all` in the app.
